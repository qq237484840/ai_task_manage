# BUG-006 —— M001 `default_parser` 无条件静默 Mock 兜底，绕过 `AT_AI_ALLOW_MOCK_FALLBACK=false`

- **BUG ID**：BUG-006 ｜ **状态**：**`Fixed`（2026-09-14，`Task-016` 修复；全量回归 251/0/0/0 + API 面红→绿 + 写区双证）** ｜ **发现日期**：2026-09-14
- **发现者**：Project Master（真实三方 AI 联调期间**自然复现**，非人为注入）
- **影响范围**：`backend/app/modules/m001/services/task_parser.py::default_parser` + `task_service.py` 解析落库与 `tasks.spec_status`
- **严重级别**：**高**（在「真实三方 + 禁用 Mock 兜底」的**显式配置**下，AI 解析失败被伪装为成功 `spec_status=parsed`；用户与验收均无法察觉 AI 未实际执行 —— 违反 `ADR-011` 降级策略的可配置语义，构成与 `BUG-004` 同类的「静默降级」）

## 1. 现象（2026-09-14 真实环境自然复现）

**配置**：`AT_AI_PROVIDER_MODE=real`、`AT_AI_ALLOW_MOCK_FALLBACK=false`，LLM/Vision/OCR 三类 Provider 凭据齐备（真实三方）。

1. `POST /api/v1/tasks`（文本源 `"数学：练习册 P23 第 1-10 题；语文：背诵第三课"`）→ **`201`，`spec_status="parsed"`，`contents = [('math','练习册 P23 第 1-10 题'), ('chinese','背诵第三课')]`** —— 界面呈现为「AI 已解析」。
2. 但同期 DATA-009 记录：

   ```
   capability=task_spec_parse  provider=openai_compatible  model=glm-5.3  mock=0  status=error
   ```

   → **AI 从未成功产出**（三方转发失败），真实草稿来源 = `mock_parse_sources` 本地启发式。
3. AI 产物与该 Mock 产物在简单样本上**不可区分**，UI / API 响应**均无降级信号**；只有查 DATA-009 才能发现真相。

**对照（同配置下 M002 侧行为正确）**：照片挂接建议的真实 Vision 调用失败 → 照片保持 `unassigned`、`links=[]`（`AiUnavailableError` 不兜底）→ 证明「禁兜底」语义在 M002 侧被正确实现，**M001 侧未对齐**。

## 2. Root Cause

| # | 环节 | 证据 |
| --- | --- | --- |
| 1 | AI 抛错 / 返回不合规后，**无条件**回落 `mock_parse_sources` | `task_parser.py:198-207`：`try: outcome = parser(session, sources=ai_sources); coerced = _coerce_draft(outcome); if coerced is not None: return coerced` → `except Exception as exc: logger.warning(...)` → `:207` `return mock_parse_sources(sources)` |
| 2 | 全程**不读** `AISettings.allow_mock_fallback` | `task_parser.py` 全文无 `get_ai_settings` / `allow_mock_fallback` 引用（本次联调前为 0 处；`provider_mode` 亦不参与判定） |
| 3 | 「AI 返回不合规（`coerced is None`）」与「AI 抛错」两条路径**同等静默兜底** | 同上：`:203` 为 `None` 时不返回 `None`，继续走到兜底 |
| 4 | 上层依 `default_parser` 非空结果置 `spec_status=parsed`，该字段**不区分来源** | `m001/services/task_service.py` 解析成功后置 `parsed`；`tasks` 无 `parse_source` 类字段 |

**为何既有全量回归（237 例）未发现**：M001 解析用例断言的是**文本内容**，而 AI 与 Mock 在「学科：内容」这类简单样本上输出一致；且 Mock 用途例走 `provider_mode=mock`（显式 Mock 非降级，兜底语义本就允许）→ **「real + 禁兜底」路径无用例覆盖**。此即 `BUG-002` 教训的同类形态：正确的替身（Mock）掩盖了真实缺口。

## 3. 建议修复方案（不在本单执行）

**推荐方案（最小破坏，无表结构变更）**：

1. `default_parser` **感知 `allow_mock_fallback`**：当 AI 未产出合规结果（抛错或 `coerced is None`）时 ——
   - `get_ai_settings().allow_mock_fallback is True` → 维持现有兜底（现状）；
   - 为 **`False` → 返回 `None`** → 上层保持 `spec_status="placeholder"`（与 M002 侧禁兜底语义一致）。
2. 保留并强化既有 `logger.warning`（降级可观测），DATA-009 错误记录已随 `session` 落条（`BUG-004` 修复成果），无需新增字段。
3. 补充**判别力用例（红→绿）**：`AT_AI_ALLOW_MOCK_FALLBACK=false` + 注入必然失败的 Provider → 断言 `default_parser(...) is None` 且 `POST /tasks` 后 `spec_status == "placeholder"`；还原 `true` → 断言兜底生效、`parsed`。

> **硬约束**：不得删除或放宽既有 `xfail` 哨兵（`test_bug003_*` / `test_bug004_*`）；不得新增 `try/except TypeError` 式签名兼容；不得改动 `app/core/ai/**`（`ADR-011` 横切层归属）。

**备选方案**：保留 `parsed`，新增 `tasks.parse_source`（`'ai' | 'mock' | None`）并 API 暴露 —— 需 **CR + API 契约 + DATA 模型修订**，成本显著更高；仅当用户要求「兜底但需可区分来源」时才考虑。

## 4. 契约与影响面

- 推荐方案**不改表结构、不改 API 响应契约**，仅按既有配置语义调整 `spec_status` 取值 → 属缺陷修复。
- **行为变更面（必须写 Release Note / CHANGELOG）**：`allow_mock_fallback=false` 场景下，AI 失败的任务将由「已解析」变为「**待解析**」（此即配置意图，用户可手工补录）；需同步评估对既有验收剧本 4 的影响。
