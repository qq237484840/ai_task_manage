# BUG-007 —— 「重试建议」在真实模型下必然前端超时（全局 15s < 同步 AI 调用 >15s）：成功却报失败

- **BUG ID**：BUG-007 ｜ **状态**：**`Fixed`（2026-09-14，`Task-017` 修复；含 `Task-017 §3.3b` 最小扩权使作业页同一路径一并修正）** ｜ **发现日期**：2026-09-14
- **发现者**：Project Master（`REQ-011` 需求 grill 期间读码 + 真实联调实测发现）
- **影响范围**：`frontend/src/api/http.ts`（全局 timeout）× `API-M002-007`（同步执行 AI）× 前端重试入口
- **严重级别**：**中-高**（功能「看似可用、实际必失败」；Mock 下快而掩盖，**仅真实三方暴露**）

## 1. 现象

1. 「作业」页照片卡片的「重试建议」按钮（`PhotoListView.vue:561-566` → `getLinkSuggestions(photo_id, true)`）。
2. 前端 axios 全局 `timeout: 15000`（`http.ts:26-29`）；而 `retry=true` 在**请求内同步**执行 AI（`link_routes.py:42-45`）；真实模型单次实测 **15 630 ms**（DATA-009：`photo_link_suggest / qwen3.8-flash / mock=0 / status=ok / 15630ms`）。
3. → **15.6s > 15s**：前端先超时，用户看到「网络异常，请检查后端服务是否已启动」类提示（`http.ts:73-78`）；**但后端此时已完成并写入挂接建议**（照片实际已变 `suggested`）。
4. 用户重进页面或刷新后才看到「其实成功了」——**成功却报失败**，且极易被误判为「后端挂了」。

**为何此前未被发现**：Mock Provider 下该调用近乎瞬时（毫秒级），**全量回归与既有浏览器级验收均在 Mock 下跑**（`mock-vision`），故超时从未触发。

## 2. Root Cause

| # | 环节 | 证据 |
| --- | --- | --- |
| 1 | 全局超时值 < 单次同步 AI 调用耗时 | `frontend/src/api/http.ts:26-29`（`timeout: 15000`）vs 实测 `15630ms` |
| 2 | `API-M002-007` 的 `retry=true` 为**同步**语义（在请求内跑 AI 后返回） | `backend/app/modules/m002/api/link_routes.py:42-45`（`LinkService.suggest_for_photo(...)` + `db.commit()` 后回读） |
| 3 | 前端未对该请求单独放宽 timeout，也无「长耗时任务」交互设计（无进度/轮询） | `frontend/src/api/index.ts:225-231`（`getLinkSuggestions` 无 timeout 参数） |
| 4 | 失败分支无「可能后端已成功」的提示，用户无法自诊断 | `PhotoListView.vue:561-569`（`catch → toastError`） |

## 3. 建议修复方案

- **止血（本期，`REQ-011` / `Task-017`）**：该请求**单独放宽 timeout 至 60s**（`getLinkSuggestions` 增加可选 `timeoutMs`，**不改全局** `http.ts`）；按钮 loading 文案改为「AI 分析中，约 15–30 秒」；返回 `suggestions` 为空才视为「未生成建议」，据此给出不误导的提示。
- **根治（需 CR）**：`API-M002-007` 异步化（`retry=true` 触发即返回 + 前端轮询建议状态），彻底消除长请求占用与超时耦合（已登记于 `docs/TECH_DEBT.md` 「后续候选 2」）。
- **测试要求**：前端侧应有**判别力**证据（例如以 timeout=1ms 复现「前端超时但后端成功」→ 修复后该请求不再超时）；不得只以「Mock 下点了没报错」充当证据。

## 4. 契约与影响面

- 修复**不改契约**（仅前端单请求 timeout 与文案）。
- 若选根治方案 → 需 CR（`API-M002-007` 语义由同步转异步）。

## 5. PM 复核（2026-09-14）

**结论：Confirmed**。PM 亲手取证：读码确认为同步调用（`link_routes.py:42-45`）+ 实测 DATA-009 `latency_ms=15630` 超过前端 `timeout=15000` 两个独立事实；并核对该前端调用点在真实模型下的必然性（Mock 毫秒级掩盖）。

## 7. 修复记录（`Task-017`，2026-09-14）

- **改动（2 处调用点，均只放宽单请求超时；全局 `http.ts` 未动）**：
  1. `frontend/src/api/index.ts`：`getLinkSuggestions(photo_id, retry = false, options: { timeoutMs?: number } = {})` —— 仅在传参时覆盖单请求 `timeout`（未传时沿用全局 15s）。
  2. `frontend/src/views/TaskDetailView.vue`（`REQ-011` 新增卡片）：`getLinkSuggestions(id, true, { timeoutMs: 60000 })`。
  3. `frontend/src/views/PhotoListView.vue`（**`Task-017 §3.3b` 最小扩权，仅 1 行**）：作业页既有「重试建议」同样改为 `{ timeoutMs: 60000 }` —— 否则本单**未闭环**（同一失效路径仍在）。
- **验收证据**：`vue-tsc -p tsconfig.app.json` **0 error**；`npm run build` **EXIT=0**；**浏览器级真实成功分支 6/6 PASS**（真实三方 AI：点重试 → toast「已生成挂接建议，请到「作业」页采纳」→ 照片移出列表 `rows=1→0`）；失败分支 8/8 PASS（AI 不可用时如实提示，不谎报成功）；后端全量 `pytest` **251 / 0 / 0 / 0**（用例数不变 → 前端改动对后端零影响）。
- **判别力依据**：`latency_ms=15630 > timeout=15000`（DATA-009 实测）为修复必要性的独立证据；修复后该请求拥有 60s 预算。
- **未取证的边界（诚实标注）**：浏览器级**未**构造 >15s 的真实长请求（避免依赖外部中转稳定性）→ 60s 放宽为**静态证据**（代码）；根治方案（`API-M002-007` 异步化）已登记为 CR 候选。
- **残留提示**：前端无自动化测试框架，本次为临时浏览器脚本取证（已删除）；长期回归建议另立任务引入前端 E2E。
