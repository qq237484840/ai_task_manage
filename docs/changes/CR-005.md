# CR-005：布置单图片源解析通路打通（链路 T 图片源 → Vision）+ 任务「重新解析」端点

- **提案人**：Project Master ｜ **日期**：2026-09-14 ｜ **状态**：**`Approved`（用户批准 2026-09-16）→ 执行中**（契约修订完成 → 拆 `Task-018`~`Task-021`）
- **关联需求**：`REQ-011` **第二阶段（A1）** ｜ **关联历史成因**：`BUG-004`（图片源不转发的成因之一）
- **变更类型**：**契约变更**（M001 新增端点 + M001/M002 内部服务接口各 +1）+ 新增跨模块回调（沿用既有唯一通道）
- **是否需 ADR/ACR**：**不需要**。理由：① 不新增模块、不改判定模型；② **不改数据所有权**——图片 Owner 仍是 M002，且由 **Owner 提供受控读取接口**，符合 `docs/DATA_MODEL.md`「数据所有权原则：其他模块原则上通过接口读取」；③ 沿用既有「**回调注册**」跨模块唯一通道（`register_links_migration_hook` 先例，`main.py` 启动期幂等自愈）。

## 1. 动机

- **现状**：M001 链路 T **只转发文本源**（`m001/services/task_parser.py::_to_ai_sources`，图片源不转发）→ **纯图片布置单永远停在 `placeholder`**（用户 2026-09-14 实测「待解析」的根因）。
- **目标**：家长拍/传布置单照片后，可由 AI（**Vision**）解析出「学科 + 内容项」草稿；并可在任务详情页**重新解析**（AI 失败后的重试）。

## 2. 变更内容

### 2.1 M001 —— 新增「布置单图片读取」回调槽

- 新增 `register_task_spec_image_provider(fn)` 与槽 `_task_spec_image_provider`（**与 `aggregation_service.register_links_migration_hook` 完全同模式**：M001 定义槽 → M002 **导入期**注册 → `main.py` **启动期**幂等自愈）。
- `_to_ai_sources`：对 `kind=image` 且带 `photo_id` 的源 → 经 provider 取 `{mime, abs_path}` → 构造 `ImageInput(mime=…, path=…, image_id=photo_id)` → `SourceInput.image_of(...)`。
- **防伪造硬约束（`BUG-004` 教训）**：**仅当 Vision Provider 为真实（`provider_mode` 走真实且未 degraded）时**才转发图片源；Mock / degraded 时**维持现状不转发**（→ `placeholder`），杜绝 Mock 产出占位草稿冒充解析结果。
- provider 未注册 / 取不到文件 / 归属校验失败 → **不转发该源**（不报错、不伪造）。

### 2.2 M001 —— 新增端点 `API-M001-022`（重新解析）

- `POST /api/v1/tasks/{task_id}/reparse`（Bearer）
- 语义：对**未确认**任务重跑链路 T；结果处理见 §2.4；**与任务状态（draft/published/closed）无关**（只写 `spec_status` / `contents`）。
- 响应 `200`：**与 `GET /tasks/{task_id}` 同构的 `TaskDetailDTO`**（当前态）。
- **失败语义沿用 `BUG-006` 修复后的口径**：AI 不可用且禁兜底 → **不抛错**，返回当前 `TaskDetailDTO`（`spec_status` 保持 `placeholder`），由前端如实提示。
- Errors：`401`；`404`（任务不存在/越权，对外 404）；`409 spec_confirmed`（已确认任务拒绝重解析）；`500`。
- 契约：`docs/modules/M001/MODULE_API.md` **v0.2.0 → v0.3.0**（新增 1 端点 + 内部服务接口表 +1）。

### 2.3 M002 —— 注册受控图片读取 provider

- 新增 **`provide_task_source_image(session, family_id, photo_id) -> TaskSourceImage | None`**：
  - 校验 `family_id` 归属（查无 → `None`）；解析受控路径（复用既有 `ImageStore(settings.image_root).abs_path(photo.normalized_path)`）；
  - 返回 `{mime, abs_path}`；**路径不进入任何 API 响应**（与既有 `API-M002-004` 一致：路径仅限同机进程内消费）。
- 导入期注册 + `ensure_task_spec_image_provider_registered()`；`main.py` 启动期幂等自愈。
- 契约：`docs/modules/M002/MODULE_API.md` **v0.4.1 → v0.4.2**（内部服务接口表 **+1**，供 M001 反向消费）。
- **实施期修正（2026-09-16，PM 裁决，`Task-018` 实施中发现）**：原签名 `(family_id, photo_id)` **补入 `session`**（→ `(session, family_id, photo_id)`），理由：`app/core/database.py` 明确「**不在此处持有隐式全局库连接**」（引擎/会话仅来自应用装配或测试 fixture），provider **必须复用调用方事务会话**；且与 M001↔M002 既有内部接口惯例（`list_groups(session, family_id, ...)`）一致。**M001 侧槽调用同步为 `fn(session, family_id, photo_id)`**（`default_parser` 已有 `session`，见 §2.1）。属**签名完善（非破坏性）**：契约刚发布、**尚无消费者**，故直接修订契约文本并记录于此。

### 2.4 内容项处理规则（**关键语义，必须逐字实现**）

| 当前 `spec_status` | 解析成功 | 解析无草稿 / AI 失败 |
| --- | --- | --- |
| `placeholder` | 写入内容项 → `parsed` | **不改动**（保持 `placeholder`） |
| `parsed`（未确认） | **整体替换**既有内容项（以本次为准）+ 审计 | **不改动**（幂等，**不得清空**已有内容项） |
| `confirmed` | **拒绝**（`409 spec_confirmed`，不执行） | 同左 |

### 2.5 前端

- 任务详情页新增「**重新解析**」按钮：`placeholder` / `parsed` 可见；`confirmed` 隐藏（或禁用 + 提示「已确认，需先取消确认」）。
- 复用 `BUG-007` 修复模式：该请求**单请求放宽 timeout**（真实 Vision 约 15s+）。
- 上传（「任务」入口）成功后，若 `spec_status=placeholder` → 提示「可直接在任务详情页重新解析」。
- 完整处理（编辑/确认草稿）仍走既有 `TaskEditorView`。

| 维度 | 影响 |

## 4. 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| **Mock 伪造草稿**（`BUG-004` 教训） | §2.1 硬约束：仅真实 Vision 转发；Mock/degraded → 不转发；并加**防伪造专项用例** |
| 真实模型对「布置单照片」识别不达标 | 保持 `placeholder` + 手工补录（`TaskEditorView`）兜底；本 CR 只负责「通路 + 重试」 |
| 长耗时导致前端超时 | 复用 `BUG-007` 修复模式（单请求放宽 timeout） |
| 重复解析产生脏数据 | §2.4 覆盖规则（`confirmed` 拒绝、失败不清空） |
| M002 未就绪时 M001 行为 | provider 未注册 → 不转发（等同现状，**不回归**） |

## 5. 验收要求（批准后写入任务书 DoD）

1. 纯图片布置单（`kind=task_spec` 照片）→ `POST /tasks/{id}/reparse` → **真实 Vision** 下产出学科+内容项草稿 → `spec_status=parsed`；DATA-009 `capability=task_spec_parse / mock=0 / status=ok`；
2. **Mock / degraded 下不伪造**（仍 `placeholder` 且 `contents==[]`）—— 判别力用例（红→绿）；
3. `confirmed` 任务 reparse → `409 spec_confirmed`；
4. §2.4 三种情形逐条用例（含「解析失败不清空既有内容项」）；
5. M002 provider 归属校验用例（跨家庭 → `None`，不得越权取图）；
6. 全量 `pytest` 用例数不减（基线 251）；
7. 前端 `vue-tsc -p tsconfig.app.json` 0 error + `npm run build` EXIT=0；
8. 浏览器级：任务详情页「重新解析」可达并如实反馈（成功/失败）。
