# ADR-007：AI Provider 接入策略 —— 抽象 + Mock 先行（PD-006）

- **状态**：Accepted
- **日期**：2026-09-08
- **决定者**：用户（PD-006 确认）+ Project Master
- **关联**：`docs/PROJECT_STATUS.md`（PD-006）、`docs/ARCHITECTURE.md`（AI Provider 抽象层）、`docs/DATA_MODEL.md`（DATA-009）、REQ-008

## Context

V1 全链路依赖三类 AI 能力：图像视觉（版面/质量）、OCR（文字结构化）、LLM（评价与建议生成）。真实三方服务需要密钥与选型（RISK-001），而 V1 要求"每版本可在本地独立真实运行验证"，AI 调用还必须全程可追溯（DATA-009）。

## Problem

在真实 Provider 密钥与选型未定之前，如何让开发与验收不被外部依赖阻塞，同时保持"可追溯、可替换、不绑定单模型"？

## Options

| 方案 | 说明 |
| --- | --- |
| A. **抽象 + Mock 先行**（采用） | 定义 Provider 抽象，内置 Mock/演示实现（无需密钥本地跑通全链路）；真实实现按统一接口后补替换 |
| B. 直接接真实三方 API | 需要用户先定选型并准备密钥，外部依赖阻塞开发启动 |
| C. 本地开源模型 | 离线免密钥，但部署重、硬件要求高，拖慢 MVP |

## Decision

- 固定三类 Provider 抽象，业务只面向接口：
  - `VisionProvider`：版面检测、图像质量评估、预处理建议
  - `OCRProvider`：文本识别与结构化（行/块/置信度）
  - `LLMProvider`：结构化抽取、评价与建议文本生成
- V1 默认实现为内置 **Mock/演示 Provider**：基于可复现的确定性规则/样例输入产生输出（含模拟低质量图片与低置信分支），**本地无外部密钥即可跑通 识别→匹配→评分→评价→报告** 全链路
- 全部 AI 调用（含 Mock）统一经调用入口写 DATA-009：`model/prompt_version/request_id/input_ref/latency/token_usage/result/confidence/error`；Mock 的 `model` 字段使用 `mock-*` 命名
- 真实三方接入 = 新增实现类 + 配置切换 + `EXTERNAL_SYSTEMS.md` 登记，**不改任何业务代码**；不破坏既有验收路径（保留 Mock 配置用于回归/演示）

## Reason

- 契合 V1"每版本可独立真实运行验证"：无 key 也能完成全链路验收与演示
- 可追溯架构（ADR-003/REQ-008）不依赖真实 AI 即可先行落地
- 单模型绑定被彻底隔离；未来替换/多供应商只发生在 Provider 实现层

## Consequences

- Mock 输出的确定性便于单测与验收断言；真实服务接入后行为差异由模块验收把关（必要时回归 Mock）
- RISK-001（AI Provider 未定）降级为"仅影响真实效果质量验证，不阻塞开发"
- `EXTERNAL_SYSTEMS.md` 在首个真实接入时创建；Provider 配置项登记入 `CONFIGURATION.md`
