# ADR-013：作业归属与判定的双层模型 —— 按天事实层 + 跨天聚合层（判定落聚合层，取代 ADR-010 的判定粒度）

- **状态**：**Accepted**（2026-09-10，随 `CR-003` 批准生效）
- **日期**：2026-09-10
- **决定者**：用户（grill 定稿 A~F）＋ Project Master
- **关联**：`docs/requirements/CLARIFICATION-2026-09-10.md`（需求澄清定稿，权威源）、`docs/changes/CR-003.md`、`docs/adr/ADR-010.md`（判定粒度 **Superseded**）、`docs/adr/ADR-003.md`（不武断底线，**继续适用**）、`docs/DATA_MODEL.md`（DATA-001 修订、DATA-012~018）、REQ-001/002/003/004/005/007

## Context

需求澄清（2026-09-10）确立三条事实：

1. 任务（布置）是**按天**产生的：由照片/文本经 AI 解析得到，家长不需要手工录入；上传时间以**凌晨 4 点**为日界（9/9 20:00 与 9/10 03:00 同归 9/9）。
2. 展示与加工是**跨天聚合**的：周一到周四按天显示，**周五~周日合并为"周末作业"**，每周按周次分组，假期按自然周分段。
3. 完成情况是**跨天**的：周末作业的实际完成可能是"周五完成一部分 / 周六未做 / 周日完成一部分"等任意组合，而任务（布置）可能只在三天中的某一天上传。

## Problem

**判定（完成情况分析与家长确认）应落在哪一层？**

- 若落**天粒度事实层**：周末跨 3 天，任务可能只在其中一天上传，某天根本不存在对应子任务 → "每天的判断"不成立，会产生大量逻辑矛盾（判定对象缺失、同一份作业被拆到多天、跨天完成无法归属）。
- 若落**聚合层**：判定对象 = 该次聚合的学科子任务，与"上层数据清洗加工都按聚合逻辑、最终展示为聚合任务"的需求表述一致。

同时衍生问题：**聚合规则（周末划分、4 点边界）变更后，历史怎么办？**

## Options

| 方案 | 说明 | 结论 |
| --- | --- | --- |
| A. 判定落事实层（按天） | 天级判定对象、天级完成结论 | ❌ 周末跨天场景逻辑矛盾（见 Problem） |
| B. 判定落聚合层，聚合**实时计算** | 不落库，每次按当前配置实时聚合 | ❌ 配置一改历史展示立即全变，与"配置变更只管后续、不影响历史"直接冲突 |
| C. **判定落聚合层，聚合落库固化**（采用） | 聚合对象与成员落库；`policy_version` 锁定生成时的配置版本 | ✅ 逻辑自洽 + 历史稳定 + 无需数据迁移 |

## Decision

1. **双层模型**
   - **事实层（按天）**：`tasks` 唯一键 **`(student_id, category, belong_date)`**；只承载"哪天、通过什么输入源、布置了什么内容项"。**不承载判定**。
   - **聚合层（跨天）**：`task_groups`（成员 = 若干天任务）→ `task_group_subjects`（按学科合并，**★判定单元**）→ `photo_subject_links`（作业照片 N:N 挂接）→ `completion_analyses`（完成结论草稿/确认）。
   - **每个 `belong_date` 都有一个聚合**（最小聚合 = 1 天），展示、挂接、判定、报告**走同一条代码路径**，仅"成员集合"不同。
   - **子任务(学科)位于聚合层**（`task_group_subjects`）；原先设想的天任务下 `task_subjects` **取消**。
2. **挂接与判定粒度** = 聚合子任务(学科)级，允许 **N:N**（1 照片 → 多学科；1 学科 → 多照片）。**ADR-010 的"内容级逐题判定"粒度作废**——这是需求修正，不是新增第二套判定。
3. **配置锁定语义**
   - 配置（`AT_DAY_CUTOFF`、周末/假期聚合规则）变更**只影响未聚合的对象**；**已聚合的按生成时的配置**继续成立。
   - 锁定**粒度** = 每个 `(学生, 聚合对象)` 独立锁定（同日不同学生可用不同配置版本）。
   - 锁定**触发** = 数据写入（任务解析完成 / 作业照片上传）；**纯浏览不锁定配置**。
   - 实现：`task_groups.policy_version`，生成时写入当时生效版本，后续**追加数据不改**该字段。
4. **"固化"的准确含义 = 配置不回溯、数据可增补**：不因**配置变更**重算已有聚合；但必须支持**新数据追加**进已有聚合（周末聚合在周五即可能生成，周六/周日数据需追加）。
5. **事实字段写入即固化**：`belong_date` 于上传时按当时配置计算并落库，之后配置变更**不回算历史**。手工改归属日走 §Consequences 的 5 条连锁规则。
6. **继承 ADR-010 中仍然有效的原则**：端到端直判（不维护参考答案为基准）、每判必给可观察依据、置信度、`无法判断` 出口、低置信入家长复核、不武断底线（ADR-003）——**仅判定粒度由"逐题"改为"聚合子任务(学科)级"**。

## Reason

- 与用户需求表述逐字对齐："上层数据清洗加工都按聚合逻辑；**最终展示也是聚合任务**"。
- 消除周末场景的判定逻辑矛盾（周五/周六/周日任意完成组合都能落到同一个判定对象上）。
- 聚合落库 + `policy_version` 使"配置变更只管后续"**天然成立**，且**无需任何历史数据迁移**（方案 B 做不到）。

## Consequences

- **`ADR-010` → Superseded（判定粒度）**；其可靠性原则由本 ADR 继承。ADR-006 仍为 Superseded。
- **`task_items` 废弃**（逐题建模不再作为判定载体），不参与 V1 写入；内容项由 `task_contents` 承载（只读展示）。
- **M002 契约需修订**：`photos` 的"1 照片 → 1 个 `(task_id, subject, group_no)` 段"强约束**放开为 N:N**（`photo_subject_links`）；`photos.subject`/`group_no` 废弃，`task_id` 保留为窗口级归属；**上传入口不再要求填写内容**。
- **M001 契约需修订**：`tasks` 增 `category`/`belong_date`/`week_index`/`spec_status` 与唯一键；新增 `task_spec_sources`；`title` 改为可自动生成（占位主任务）。
- **新增模块能力**：LLM 接入层落 `app/core/ai/`（provider 抽象 + prompt + 结果 schema 校验 + 降级）；链路 T 解析归 M001，链路 H 挂接/复核/分析归 M002。
- **手工改归属日的连锁规则**（5 条）：① 重算快照 ② 迁移主表 FK（目标聚合无则建）③ 源聚合空则删 ④ **已被完成分析消费的作业禁改** ⑤ 记审计；**另加**：跨聚合迁移须同步迁移 `photo_subject_links` 挂接目标。
- **假期**：V1 按自然周聚合；假期"完成计划"与评估报告/汇总简报**后置 V2**。
- **测试需覆盖**：4 点边界归属、周末 3 天合并、配置锁定（同日不同学生不同版本）、追加数据不改 `policy_version`、AI 降级手工挂接、跨聚合迁移。
- **风险**：聚合落库引入一层一致性维护（事实层追加 → 聚合层合并）；缓解 = 合并仅在数据写入时触发且幂等。
